# Duplex convention reference vectors

`ark_duplex_vectors.json` is the oracle `adapter/testing/duplex_test.py` holds
`ARK_0_3` and `ARK_0_5` to. It is **generated by running the two crates
themselves** — not by a second implementation of the sponge in this tree, which
would prove only that two of our own implementations agree.

## Regenerating

```bash
cd hash_frx/adapter/testing/reference/arkvec
cargo run --quiet > ../ark_duplex_vectors.json.raw
python3 -m json.tool ../ark_duplex_vectors.json.raw > ../ark_duplex_vectors.json
```

`arkvec` depends on both releases at once — `ark-sponge` at git tag `v0.3.0` and
`ark-crypto-primitives` 0.5 with its `sponge` feature. Cargo treats 0.3 and 0.5
as semver-incompatible, so the two coexist with their own `ark-ff` underneath and
nothing has to be vendored. Both built clean on rustc 1.97.

It is deliberately **not** wired into bazel. It needs a network fetch and a Rust
toolchain, neither of which the Python test legs have, and the vectors only
change when the conventions themselves do.

## What the configuration is, and why

Shared across both sides: width 3, rate 2, capacity 1, `alpha = 1`,
`full_rounds = 8`, `partial_rounds = 1`, with a small non-symmetric MDS and one
distinct round-constant row per round.

- **Width 3 / rate 2 / capacity 1** is not a choice. ark-sponge 0.3 hardcodes
  them (`rate = 2`, `capacity = 1` in `PoseidonSponge::new`, and
  `PoseidonParameters::new` asserts each round-constant row has length 3).
- **`alpha = 1` is the load-bearing one.** The two releases apply the
  partial-round S-box to *different lanes* — 0.3 to `state[len - 1]`, 0.5 to
  `state[0]` — which is the only place they disagree inside the permutation
  itself. With `alpha = 1` the S-box is the identity, so a partial round is a
  full round and that disagreement vanishes: both compute the same permutation,
  and any difference in output is the sponge schedule. Whether this repo's
  Poseidon matches ark's *permutation* is
  `poseidon/testing/poseidon_test.py`'s question, not this file's.
- **`partial_rounds` is 1 rather than 0** only because this repo's dedicated
  Poseidon XLA emitter rejects a zero partial-round count
  (`unparsable composite.attributes`). With `alpha = 1` the count does not
  matter mathematically.
- **This is not a cryptographic configuration and is not meant to be one.** An
  identity S-box makes each round an ARC followed by an invertible
  non-symmetric MDS — an affine map that is not the identity and does not
  commute with a rate read, so a skipped or extra permute is fully visible,
  which is all this fixture has to show.
- **The MDS is non-symmetric on purpose.** A symmetric one can hide a lane-order
  mistake, which is precisely the class of bug the `RateLanes` axis is about.

Field elements are emitted as canonical **little-endian bytes in lowercase hex**
on both sides. Neither release's `Display` is used: 0.3's renders the big-integer
in hex and 0.5's in decimal, and an earlier run compared those directly and
reported every script as differing for that reason alone.

## Reading the file

Each entry under `scripts` carries the absorb/squeeze program (`steps`), both
implementations' outputs, and `differs`.

**Every script differs**, which is expected and is not the spill bug: the
`RateLanes` axis moves the rate to the other end of the state, so every read
lands elsewhere. The two scripts that additionally exercise the 0.3 spill skip
are `squeeze1_then_squeeze_rate` and `absorb1_squeeze1_then_squeeze_rate`; in
those, and only those, `ark_0_3` **repeats a value** — the lane an earlier
squeeze already returned, re-emitted because the permute was skipped.

`interleaved` earns its place separately: it is the only script that absorbs
again *after* squeezing, and it is what revealed that 0.5's `absorb` dropped the
permute 0.3 ran on that switch. No absorb-then-squeeze script can see that axis,
so a reference set reasoned about rather than generated would have missed it.
